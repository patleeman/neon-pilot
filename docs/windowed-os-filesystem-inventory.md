# Windowed OS Filesystem Inventory

This is the Phase 1 inventory for the Windowed OS -> Agentic OS single-root migration. It is a migration planning document, not a statement of current product behavior.

The target from `to-do/windowed-os.md` is one user-chosen desktop root:

```text
<desktop-root>/
├── apps/
├── data/
├── documents/
├── agents/
├── logs/
└── system/
```

Current Neon Pilot state is split across `<state-root>`, `<config-root>`, `<knowledge-root>`, browser/local UI state, Electron user data, and conversation cwd metadata. Phase 3 should migrate the roots in one pass so the fork does not keep both the old per-conversation workspace model and the new desktop-root model.

## Migration Notes

1. Choose and persist `<desktop-root>` before moving any child state. The fork should not continue to ask for per-conversation working directories after this point.
2. Create a migration manifest that records old roots, new roots, timestamps, and whether each item was copied, moved, or intentionally dropped.
3. Move extension/app packages after Phase 2 deletes the cut extensions; otherwise Phase 3 will migrate apps the fork intends to remove.
4. Treat `<state-root>/neon-pilot-runtime/chat-workspaces/*` as disposable compatibility workspaces. Preserve user files only if they are not empty and not known generated scratch state.
5. Migrate conversation session metadata from "cwd is identity" to "desktop root is cwd; workspace context is a document/file reference." This touches session creation, sidebar grouping, Files, Terminal, and prompt context.
6. Keep secrets migration explicit. Keychain-backed secrets may not need file movement; file-backed `secrets.json` must preserve restrictive permissions.
7. Do not migrate telemetry UI as a user-facing Diagnostics app. Keep logs and observability data as inputs for Activity.
8. The Filesystem Authority plan in `docs/filesystem-authority.md` should become the write boundary for user/agent/app-addressed files as soon as the desktop root exists.

## Electron / Browser Profile Storage

Electron has two separate browser-state surfaces:

1. the Chromium-managed `userData` profile selected before Electron starts, and
2. Neon Pilot-owned browser state files such as workbench browser history.

Phase 3 should move the whole Electron profile under the desktop root, then migrate user-meaningful renderer preferences out of `localStorage` into typed files or backend state. Do not move Chromium subdirectories piecemeal.

## Unknowns And Follow-Ups

- Electron/browser profile storage is now inventoried above. Phase 3 decision: set Electron `userData` to `<desktop-root>/system/electron/user-data` at startup, keep Chromium-managed profile internals together, move Neon Pilot-owned browser state files to `<desktop-root>/system/electron/` or `<desktop-root>/system/browser/`, and migrate user-meaningful `localStorage` keys to file/backend state incrementally. Ephemeral `sessionStorage` keys do not need migration.
- `<state-root>/pi-agent/state/*` is now classified above. Legacy sibling storage under `<state-root>/pi-agent/sessions/` is covered in the top inventory table as read-only migration input. Phase 3 should split these stores into durable user-visible data, conversation indexes, checkpoint/recovery data, notification state, session history, and daemon callback routing instead of moving `pi-agent` wholesale.
- Extension-specific storage inside `app-state.sqlite` is key-value, not yet documents. The first documents-store migration should identify which extension records become shared collections and which stay private app data.
- The legacy `<knowledge-root>` may contain user-authored notes/projects unrelated to the OS fork. Migration should copy, not move, unless the user explicitly chooses to make the new desktop root authoritative.
- `NEON_PILOT_*` env overrides still exist for dev/test and external compatibility. The fork should prefer typed desktop-root config for product behavior and keep env overrides only for development/test launch isolation.

## Phase 3 Acceptance Checklist

- Fresh install creates exactly one desktop root and all platform-owned mutable state lands under it or a documented OS-managed exception.
- Files app opens `<desktop-root>/documents` by default and can jump to the root for system/agent folders.
- Terminal and agent sessions start in `<desktop-root>`, not a per-conversation cwd.
- Existing local installs can be migrated once with a written manifest and rollback note.
- Extension/app install writes packages to `<desktop-root>/apps` and private data to `<desktop-root>/data/apps/<app-id>`.
- Documents store writes to `<desktop-root>/data/documents` and emits document-change events.
- No Phase 3 code path creates new state in old `<state-root>/sync/pi-agent/sessions`, `<state-root>/extensions`, or `<state-root>/neon-pilot-runtime/chat-workspaces` except explicit migration compatibility code.
